## A. Executive summary

The engine is mature: the 2026-09-11 review closed every item, the live paths have strong guards,
and the timezone handling is clean. This audit found one P1 defect that affects paper trading
today, one P1 operational gap, and several P2 reliability and data-integrity defects.

1. **P1, confirmed, not fixed (needs approval):** the Python runner trades on a stale value area
   every other trading day. The runner warms up only from `db/historify.duckdb`; the 15:35 backfill
   skips a symbol that is one day stale. Proven on 2026-10-14: BREAKOUT-PY's PFC entry used the
   10-12 profile instead of 10-13. **2026-10-23 is one of the affected mornings.**

   tasks never ran on 3 of the last 6 trading days (PC woke after 09:00).
3. **P1, confirmed, fixed:** restart attribution never matched the trade side (Python 3.12 enum
   `str()`), so the 2026-09-24 multi-strategy split was dead code.
4. **P2, confirmed, fixed:** the 14:45 time-exit check read a one-share short as an API error and
   booked it closed; an API error was silently treated as a confirmed close.

Unverified: real-broker behavior of any fix (all evidence is unit tests, mocks and read-only data),
the official closing-auction price in the daily bars, and Windows behavior of `StartWhenAvailable`

  rejects a symbol whose newest session is not the calendar's previous session, or whose previous
  session has fewer than 324 continuous 1m bars or none from 15:10 (special sessions exempt).
  Calendar unavailable: every symbol rejected. Rejected symbols are excluded for the day, logged
  CRITICAL, and alerted once a day (`runner_warmup_rejected`, delivered at every notify level).

### 4. EOD fill-capture timing (proposal only)

- Evidence: since 2026-09-24 the sandbox has no fill at or after 15:25 (`db/sandbox.db`

### 6. Order-acceptance persistence (design only)

Windows today: W1 the entry order is in flight (no local record); W2 the broker accepted it but
`save()` runs only after the stop, the fill fetch and the bad-fill guard. A crash in W2 leaves a
broker position with no `trades.db` row; restart logs "no entry trade in trades.db today" and does
not restore it.

- **Option A (recommended first):** write the normal SUCCESS entry row immediately after
  `send_order` returns SUCCESS (fill_price NULL), keep its row id, and UPDATE it with the fill price
  and context afterwards. The bad-fill guard updates the entry and inserts its exit as today.
  Restart then restores the position from the row and `_retry_missing_sl` re-protects it. No new
  status value, so readers that do not filter on status (3 queries in `db.py`, 1 in
  `analysis/ledger.py`, 1 in `breakingtrade/review.py`) see the same rows as today. Needs: `save`
  returning the row id, an `update_entry_fill`, reordering in `_handle_entry` and
  `_establish_position`, crash-injection tests at each step.
- **Option B (later):** a write-ahead `PENDING` row before the send, resolved on restart against
  the order book. Covers W1 but needs every reader audited for the new status; it overlaps the
  parked branch's late-fill adoption, so it should be designed together with that branch.
- **Reconciliation addition (either option):** a broker MIS position with no matching entry row at
  restart should raise a CRITICAL alert, not only a warning.
