# Backtest Engine Readiness

Implementation status of the capabilities that `research/STRATEGY-ONBOARDING-CHECKLIST.md`
(sections E and F) requires. The checklist is the stable contract; this file is the moving
status and is the only place that records what is built.

A run may claim full evidence-package compliance only when the required capabilities are
implemented and verified. Until then the run record lists what is missing, and the verdict
cannot be EDGE while any P1 item is absent.

Baseline: keyword search of `signal_engine/backtest/` on 2026-10-02 found no MAE/MFE, run
manifest, Monte Carlo or point-in-time universe code. Costs, slippage, walk-forward, regime,
portfolio turnover and benchmark helpers and a random-entry baseline exist in some form and
must be verified before being relied on. Status values: not started, in progress, built,
verified. Update the row, code location, test and date when status changes.

Definition of verified (owner decision 2026-10-08): implemented, acceptance tests pass, the applicable
cross-cutting requirement (see "Tests the P0/P1 work must include") is explicitly mapped, and the capability
is demonstrated on at least one real recorded run where such a run is applicable. Where a real run is not
meaningful or possible, the row states the alternative verification evidence. A row whose implementation
carries a stated limitation against its own wording (for example universe membership that is not
point-in-time) is not marked verified while the limitation stands.

Build plan for the first three P1 steps (spec schema, assumption ledger, run manifest):
`BACKTEST-ENGINE-P1-PLAN.md`. Backtests page requirements and their plan:
`BACKTESTS-UI-TECHNICAL-REQUIREMENTS.md`, `BACKTESTS-UI-PLAN.md`. Canonical lifecycle and
minimum run schema (wins on conflict): `BACKTEST-LIFECYCLE-AND-RUN-SCHEMA.md`.

A recorded run is therefore reproducible at its recorded commit, not on a later HEAD (`--reproduce` on another commit reports the failed check `code commit differs: run used <sha>, working copy is at <sha>` and never raises); `--reproduce` refuses to rerun when the commit differs, by design. The tick-grid setting is read from the frozen profile, so a run frozen before engine 1.2 keeps `tick_grid = none`.
- G6.4 part A tier source (2026-10-08): the first real run (IDEA-029 v2) flagged 29 of 26,144 stops as off the exchange grid. The sampled cases were splits and bonus issues, where the previous month's raw close put the stock in the wrong tier. The tier now comes from the previous month's close restated into the trade session's price units (adjusted close divided by that session's price factor). The v2 record is sealed with the earlier check and keeps its G6.4 fail; a rerun on the corrected check supersedes it.
- Known limitation of the production stop rule, found by G6.4 part A (2026-10-08, IDEA-029 v3): `features/instruments.safe_tick` picks the tick for a stop trigger from the tier of `price x TIER_DRIFT` (1.5), because the exact tier comes from the previous month's last close, which the executor does not have at order time. The rule is valid only while the stock has not fallen by more than one third (1 - 1/1.5) below that close. Past that, `safe_tick` returns a finer tick than the exact tier, and the trigger can be off the exact grid. Evidence: RBLBANK, previous month-end close 290.9 (exact tick 0.05), stop 155.51 on 2020-03-25 and stop 165.34 on 2020-03-27, a fall of 46.5% from that close; `safe_tick(155.51)` is 0.01, so both stops sit 0.2 of a 0.05 tick off the exact grid. 2 of 26,144 stops in v3. This is a live-execution design issue, not a G6.4 evaluator defect: the evaluator is correct and G6.4 stays a hard FAIL. The gate is not weakened and the two stops are not accepted as exceptions. Changing `TIER_DRIFT` is a live-order change that needs its own change and review; no live code was changed. Run records: IDEA-029 v2 is sealed historical evidence of the earlier tier-source defect in the check (29 stops, mostly splits and bonus issues); v3 is the authoritative evaluation of the current code and configuration (2 stops). Neither is rewritten.
- G4.1 parameter perturbation (2026-10-09): built and checked on real data. A one-off unrecorded diagnostic ran all 24 one-at-a-time +-20% neighbours of IDEA-029 v3 (12 tunable parameters; the bounds are in `VwapReversion.param_meta`): all 25 runs completed with no exception, in about 101 minutes with a 4.4 GB peak. Result: all 24 variants are net negative. Net R stays within -0.2218 to -0.2260 around the base -0.2241, net bps and the out-of-sample figures agree, and trade counts swing from 12,892 to 37,576. Changing any parameter moves how often the strategy trades but not what a trade earns: a broad no-edge plateau, not parameter fragility. It does not suggest a parameter sweet spot, so tuning the knobs is not the next move for this idea. The detailed table is kept with the diagnostic and is not part of the run record. The base-replay guard caught a real defect on this data: the replay dropped the price factor, so its stops snapped on adjusted prices and 1,258 of 26,144 trades differed from the headline run. It is fixed and now covered by a trade-for-trade regression test. A recorded run whose base net R is not positive stops at `base_not_positive` and fails G4.1 without running variants, so the neighbours are not run again. Variants are diagnostics and are not trials.
- G5.2 live caps, validation of a replay from recorded trades (2026-10-09, IDEA-029 v4, scratch prototype, not committed). The replay applied the price band (300 to 5,000 on the raw entry price), 10 trades per day, the daily (gross, 4%), weekly (net, 8%) and monthly (net, 15%) loss limits at a 1% risk fraction compounding on day-start equity, and the slot limit, first come first served. Reproduced faithfully: the price band (42.6% of the trades entered outside it, and it removes every signal of that symbol at that price, so it frees nothing for re-entry) and the trade-count rule. Reproduced only approximately: the loss limits. The daily limit in live also counts unrealised loss; counting each open trade's full adverse excursion as a pessimistic bound moved the one-slot daily removals from 23 to 62 and left the kept trades unchanged. The limits are pooled across live strategies; giving this strategy the whole allowance against a quarter of it moved the one-slot kept trades from 6,644 to 2,079. The risk fraction, 0.25% against 1%, moved them from 8,358 to 6,644. Not reproducible from the record: what a symbol freed by a removed trade would have traded next. The engine skips signal evaluation while a position is open, and `POSITION_OPEN` is stored only as a per-bar count, so no suppressed signal is recorded. At one slot the caps removed 8,367 in-band trades against 6,644 kept, so trades that would have replaced them could be a large share of the capped book and their quality is unknown. Net expectancy per trade stayed between -0.224 and -0.232 R across every variant, which is true of this losing strategy and says nothing about a profitable one. Consequence: G5.2 is `not_evaluated`. It had been a non-blocking `report` of a generic slot sweep, which hid this limit. The exact route is a re-run of the engine with the live caps vetoing entries and the affected symbols re-simulated until the capped book stops changing; it needs an opt-in engine veto and a recorded stage, and awaits owner approval. Update 2026-10-09, the exact route is built: the engine gains an opt-in entry veto and a chronological portfolio scheduler (`backtest/live_caps.py`), so a vetoed signal opens no position and the symbol keeps trading by the strategy's rules. On IDEA-029 v4 (unrecorded diagnostic, 17 minutes for the stage, 7.7 GB peak memory) the unlimited gated pass reproduced the headline run exactly (26,144 trades, net -0.2241 R, net -15.7211 bps). At the primary 1 open position the capped book was 6,635 trades at -0.2230 R per trade (2 slots: 7,017 at -0.2332 R; 3 slots: 7,165 at -0.2315 R), against 6,644 at -0.2241 R from the first-come-first-served filter, so for this strategy the trades freed by a veto changed little. G5.2 for IDEA-029 would fail the +0.05 R bar. Remaining approximations: pooled limits given the whole allowance, unrealised loss marked at 5-minute closes, nominal 1% risk. Nothing was recorded for v4.
